# 抢卡响应路径与验证

本次优化优先缩短发现候选到提交的本地等待，保持现有界面、任务配置与检查间隔。库存可见、匹配通过、平台接受请求和实例实际运行是四个不同阶段，不能用一个本地基准代替真实抢卡成功率。

## 当前路径

1. **调度与账号核验**：按 `nextCheckAt` 选取到期任务，确认任务归属。任务和用户页面操作共用一把锁；一个只读批次内部允许有限并发。
2. **库存预筛**：新租任务按所选地区顺序派发型号查询，最多两个查询同时进行。遇到非零或未知库存就停止派发，取消其余在途查询，等待收尾后进入主机匹配。只有全部地区都明确为零时才省略主机列表。看板仍读取完整目录。
3. **精确匹配**：按用户的地区、型号、卡数、驱动、容量和价格条件读取官网表格，找到候选立即停止继续扫描。
4. **准备与校验**：复用本轮页面，重新读取候选当前规格；实例基线与表单准备并行，余额保护按原规则执行。
5. **提交与对账**：操作意图、点击边界即时落盘；提交后核对绑定实例。结果不明确时先对账，不因超时重复下单。

型号筛选有官网自身的 500ms 防抖。仅等待加载图标消失，或把固定等待改短，都可能读取上一轮表格。对于实际改变型号的操作，应先监听本轮对应请求，再核对响应与表格内容；已是目标型号时无需等待新的请求。

## 本次改动

- 到期任务完成后接续下一任务，取消原来每个任务额外等待一个 500ms 调度刻度的开销；保留正常间隔、随机抖动、错误退避与通知心跳。
- 已排队的页面读取可以在两轮任务之间取得操作锁，避免连续任务使用户操作一直等待。
- 新租预筛遇到首个非明确零库存地区就返回，不再等其余地区查询完才开始匹配。
- 地区查询使用两个并行 worker；网页凭据留在浏览器内，取消信号直接传给 fetch。批次返回前没有遗留读取，之后才允许主页面导航。身份变化和已确认登录失效优先于库存命中。
- 候选定位后直接重读当前页，省略第二次扫描及其加载等待。移动到前后页、候选消失、库存或价格变化仍按原规则处理。

## 可复现对比

在项目目录运行 `node scripts/performance-benchmark.mjs`，比较旧版 500ms 周期调度与新版调度。它仅使用内存合成任务和即时空库存响应，不读取 `.runtime`、不联网、不打开 AutoDL。

本机 Windows 的一次测量中，12 个同时到期任务的最后一个启动时间从 **6085ms 降至 183ms**；这是调度排队开销，不是完整抢卡耗时。系统计时器精度与电脑负载会影响数字，测试不以绝对毫秒数作为通过条件。

运行 `node scripts/inventory-prefilter-benchmark.mjs` 可复跑六地区预筛合成对比。对照组是上一轮的**串行早停**，并非每次读取全部地区；两组都执行真实查询函数。普通请求延迟 100ms，慢首区场景的第一个地区延迟 800ms，每场景三次取中位数。

| 场景 | 串行 → 并行请求数 | 串行 → 并行耗时 |
| --- | --- | --- |
| 第一个地区有卡 | 2 → 3 | 216ms → 217ms |
| 第三个地区有卡 | 4 → 5 | 433ms → 323ms |
| 首区慢、次区有卡 | 3 → 3 | 1032ms → 217ms |
| 所有地区明确无卡 | 7 → 7 | 763ms → 437ms |

请求数包含一次地区目录读取。并发组最高在途数为 2，所有批次返回时在途数为 0；命中场景取消了一个多余查询。首区本就很快时基本没有提速，还会预发一个额外查询。收益主要来自多地区遍历和慢请求；取消只能停止本地继续等待，不能撤回平台已经收到的请求。

本轮没有缩短任务检查间隔。单地区预筛只有一路请求；多地区固定两路，遇到限流或网络失败后走原有退避，不立即重发。付费提交没有并发或竞速重复发送。

## 审查边界与下一步

v1.5.0 的 636 项自动测试通过，覆盖调度、库存缺项、账号切换、任务恢复、付费意图持久化、费用核验、结果不明和安装更新交接；原实例开机、提交判断、任务监测和市场页面另通过隔离浏览器验收。异常轮次有 500ms 最早重试边界，避免状态写盘失败后出现零延迟忙循环。完整发布验收见 [v1.5.0 检查与验证](RELEASE-1.5.0.md)。

`npm.cmd run test:parallel-inventory` 用真实 Chromium 和拦截的合成响应验证慢请求取消、全零遍历、429 限流和账号切换；禁用外部域名解析，不连接真实账号。测试核对浏览器网络终结事件，确认批次结束后无遗留请求。引擎隔离测试另确认预筛中其他任务不能进入页面、暂停后迟到结果不触发付费、后台关闭等待批次结束。

本轮未更换 `selectModel()` 的全局等待。事件等待试验发现，仅匹配型号和主机 ID 不能可靠关联当前地区、卡数及同 ID 的新库存，因而没有接入生产。后续需先建立完整的请求归因及新数据渲染证据，再评估能否安全缩短此段等待。

浏览器、网络、库存竞争及平台防抖仍会占用时间。长时间页面操作仍持有串行锁，不能通过同时修改同一表单安全消除。大量已完成任务也会放大当前 JSON 全量保存成本：500 条历史任务、每条 200 条日志的合成场景，一次无库存轮次约 596ms。本轮保留持久化边界；如实际达到此规模，应将历史日志和当前任务状态拆分存储，再验证故障恢复。

普通实例和 Pro 实例不能混用接口。当前不引入未公开的付费直提交入口，也不采用冗余创建、重复开机或绕过官网防抖的办法。若要进一步评估，应分别记录排队、读取、表单准备、提交响应和运行确认的时间，比较 p50 / p95，并在同一账号、地区和网络条件下测量。

## 技术依据

- [CrazyAutoDL 的 API 实现](https://github.com/A2ureeE/CrazyAutoDL/blob/main/windows/src/main/api.js)：参考定向库存查询与目标绑定；其全量同步顺序和内部付费接口未直接移植。
- [Stop-Manually-Refreshing-AutoDL-GPU](https://github.com/cc2025cheng/Stop-Manually-Refreshing-AutoDL-GPU)：首页优先、候选冷却和提交核验已存在于本项目，不计为本次新增性能收益。
- [autodl-gpu-monitor](https://github.com/wangzhao-desgin/autodl-gpu-monitor)：参考检查防重入与实例操作互斥的思路，未复制其代码。
- [Playwright 网络等待](https://playwright.dev/docs/network)：先注册业务响应监听，再触发动作；响应返回后仍需确认页面更新。
- [Playwright 执行环境](https://playwright.dev/docs/evaluating)、[Fetch 取消机制](https://fetch.spec.whatwg.org/#abort-fetch)：Node 和网页属于不同环境，并发批次的 AbortController 在网页内创建并连接到 fetch；取消后仍等待 Promise 收尾。
- [Go singleflight](https://pkg.go.dev/golang.org/x/sync/singleflight)：同参数在途读取合并。本项目已有账号与查询条件隔离的只读合并，付费提交不参与合并。
- [AWS 超时、重试与抖动退避](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)：超时不能证明副作用未发生，重试可能放大负载。
- [The Tail at Scale，CACM 2013](https://research.google/pubs/the-tail-at-scale/)：关注排队和长尾延迟。其冗余请求思想不适用于本项目的付费操作。
- [AutoDL 普通实例与 Pro 对比](https://api.autodl.com/docs/instance_pro/)：官方开发者 API 的实例管理能力属于 Pro；当前普通实例流程不能直接换用 Pro 接口。
